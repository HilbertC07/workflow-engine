# 第一版提示词（M1：引擎内核）

> **怎么用**：Cursor 里按 `Ctrl + I` 打开 Agent，把下面「提示词正文」整段复制进去回车。
> 它会先给你一份实现方案，**你确认之后它才会动手写代码**——这是故意设计的，别跳过。
>
> **为什么第一步不做前端**：可视化编辑器只是"画 JSON 的界面"，引擎跑不通的话，画出来也验证不了。先把后端内核和一个能 curl 的闭环做出来，前端只是最后一层的皮。前端的提示词在 `02-后续阶段提示词.md`。

---

## 提示词正文（从下一行开始复制）

```
我要从零搭一个审批流引擎的后端。当前是空白项目，还没有任何代码。

【第一步：只给我方案，先别写代码】
请输出以下内容，等我确认后再动手：
1. 完整的文件清单（路径 + 每个文件的职责，一句话说清）
2. 5 张表的建表 DDL（按 .cursor/rules/approval-flow.mdc 第八节）
3. 引擎推进的核心流程说明：从"发起实例"到"流程结束"，每一步改了哪些表、哪些字段。
   用伪代码或步骤列表表达，说清会签 / 或签 / 抄送 / 驳回分别怎么走
4. 你打算暴露的接口清单（方法 + 路径 + 入参 + 出参）
5. 你认为这个设计里有风险或不确定的地方，列出来问我

【本次目标】
搭出可运行的引擎内核：
- Spring Boot 3.3 + MyBatis-Plus + MySQL 8 的工程骨架
- 5 张表：流程定义、节点定义、流程实例、任务、流转流水
- 引擎内核：解析流程图 JSON → 生成实例 → 按节点逐级推进 → 到达结束节点
- REST API：保存定义、发起实例、查询我的待办、同意、驳回、撤回、查看流转记录
- 单元测试覆盖：会签、或签、驳回回发起人、抄送不阻塞这四种场景

【必须遵守】
- 严格按 .cursor/rules/ 下四份规则文件执行，尤其是领域规则里的状态机和 JSON 格式
- 用户/角色/部门用 MockIdentityServiceImpl，不要建用户表
- 第一版只做线性顺序流，连线条件的 condition 字段留着但一律为 null
- TO_PREVIOUS_NODE 驳回策略保留枚举不实现

【明确不要做】
- 不要做前端，不要建 workflow-ui 目录
- 不要做登录、权限、Spring Security
- 不要引入 Redis / MQ / Swagger / MapStruct / Hutool
- 不要做条件分支、并行网关、超时自动审批、催办提醒
- 不要写部署相关的 Dockerfile、CI 配置

【验收标准：做完必须能这样验证，你自己先跑一遍】
用下面这个"请假流程"跑通闭环：
START → APPROVAL(部门主管李四 1002, 会签) → CC(人事王五 1003) → END

1. 保存流程定义，返回 definitionId
2. 用发起人张三(1001) 发起实例，返回 instanceId，此时 currentNodeKey 指向审批节点
3. 查询 1002 的待办，应该看到 1 条 PENDING 任务
4. 1002 同意后，流程自动经过抄送节点推进到结束
5. 查询实例，status = APPROVED；查询流转记录，能看到"发起 / 同意 / 抄送 / 结束"完整时间线
6. 再跑一个两人都同意才通过的会签用例，验证会签语义

请告诉我每一步具体用什么命令或请求调用（给出可直接执行的 curl 或 HTTP 文件），
并先执行 mvnw.cmd -q clean compile 和 mvnw.cmd test 确认编译和测试都通过。

现在，先给我方案。
```

## 你会收到什么

Agent 应该返回一份包含 **文件清单 + DDL + 推进流程说明 + 接口清单 + 风险提问** 的方案。重点看三件事：

1. **文件清单里有没有 `engine/` 包**——如果它把推进逻辑全塞进 Service，说明没读规则，让它重来
2. **推进流程里有没有提到"事务"**——生成下一节点任务 + 更新实例状态 + 写流水必须在一个事务里，分开写会在中途失败时留下脏数据
3. **它问你的风险问题**——认真回答，这是它唯一一次主动暴露不确定性的机会

## 确认话术

方案没问题就回复：

```
可以，开始写代码。按你列的文件清单顺序来，每完成一组文件就告诉我进度。
```

想调整就直接说哪里改，比如「会签驳回策略先只实现 TO_INITIATOR」「接口路径统一加 /api/wf 前缀」。
