# M1 方案评审结论 + 给 Agent 的回复话术

## 一、这份方案的判断

**整体可以放行**。分层清晰、engine 独立、用了 executor 模式、测试覆盖到四个语义场景，是合格的设计。
尤其值得肯定的是它自己发现了「code 唯一 + 覆盖式保存会让在途单读到新图」——这是自研引擎最常见的坑之一，很多实现到上线才发现。

**但有三个坑会直接让它跑不起来或留下脏数据**，必须在它动手前补进去：

| # | 问题 | 后果 | 处理 |
|---|---|---|---|
| 1 | 表用 MySQL 原生 `JSON` 类型，测试却跑 H2 | H2 对 JSON 列行为不同，**5 个测试类大概率全挂** | 所有 JSON 列改 `LONGTEXT`，Java 侧 `String` + Jackson 手动转换 |
| 2 | 同意/驳回没有并发防重 | 两人同时点、或重复点提交，会**双重推进**，生成两轮任务 | 必须 CAS 更新，影响行数 0 即报错 |
| 3 | 递归推进无迭代上限 | 图若有环（校验漏了）会**死循环打满 CPU** | 加 `MAX_STEPS = 100` 保护 |

另外三个改进项：抄送任务别用 `APPROVED`（语义错，会污染"我的已办"）、入线也要限制最多一条、`chosenUserIds` 改成按节点映射。

## 二、第 5 节四个待拍板项的结论

| 项 | 结论 | 补充要求 |
|---|---|---|
| **1. 唯一键加 round** | **同意** | 光加任务表的 `round` 不够，**实例表也要加 `current_round`**，退回时 +1，任务按实例当前 round 生成。唯一键改 `(instance_id, node_key, assignee_id, round)` |
| **3. 版本策略** | **选 A**（每次保存新插一行） | 追加两条硬要求：① 保存新版本时把同 code 其它 `ENABLED` 版本自动置 `DISABLED`；② **推进/查询在途单绝对不要校验 `definition.status`**，只有「发起」校验——否则停用旧版本会把在途单卡死 |
| **4. 保存默认状态** | **同意** | 允许传 `status=ENABLED`，不传则 `DRAFT`，启用接口照常保留 |
| **7. 依赖** | **全部同意** | `spring-boot-starter-validation` 和 H2 都加。按第 1 点改 JSON 列类型后 H2 才跑得动 |
